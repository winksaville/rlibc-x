# Goals Discussion - 20260130

Working document for exploring next directions for rlibc-x and xt.

## Overarching Vision: xt as a General Tool

**xt** should be useful beyond just cargo/rust, while focusing on cargo/rust first.

Principles:
1. **Awareness of specificity** - As we add features, be cognizant of how cargo/rust-specific a technique is vs. generally applicable
2. **Focus on cargo/rust** - But design decisions should consider future extensibility
3. **User extensibility** - Users should be able to extend xt to other cargo commands and tools
4. **Easy iteration** - CLI commands to add/modify/remove options without hand-editing TOML
5. **Automatic history** - Modifications create versioned files for easy comparison and rollback

## File Versioning Scheme

Format: `name-<seqnum:03>-<hash:08>.ts.toml`

Examples:
```
tspec-001-a1b2c3d4.ts.toml
tspec-002-e5f67890.ts.toml
tspec-003-deadbeef.ts.toml
```

Benefits:
- **Sorting works** - Sequential numbers give visual ordering
- **Hash for identity** - Content-based deduplication, detect identical specs
- **Compare friendly** - `xt compare 001 003` shows improvements or regressions

Every CLI modification creates a new file. Additional commands:
- `xt merge` - Consolidate changes from multiple versions
- `xt resequence` - Clean up gaps, reset numbering

## CLI Option Management

Quick iteration without manual TOML editing:

```bash
cargo xt set rustc.opt-level z           # Set a value
cargo xt add linker.args "--gc-sections" # Add to a list
cargo xt remove cargo.features "foo"     # Remove from list
cargo xt show                            # Display current spec
cargo xt compare 001 003                 # Compare two versions
```

## Current tspec Format

Stable format with high-level options translating to tool-specific flags:

```toml
panic = "immediate-abort"
[cargo]
[rustc]
[linker]
```

The pattern (high-level intent → tool-specific flags) is general, even if current sections are cargo-specific.

Future possibility: `[tool.cargo]`, `[tool.gcc]`, `[tool.make]` etc.

## Potential High-Level Options

### `strip`

Strip symbols from binary for smaller size.

Would translate to:
- `rustc`: `-C strip=symbols`
- `linker`: `--strip-all`

Possible values: `none`, `debuginfo`, `symbols`

### `lto`

Link-time optimization for smaller/faster binaries.

Would translate to:
- `rustc`: `-C lto=fat` or `-C lto=thin`
- `rustc`: `-C embed-bitcode=yes`
- `rustc`: `-C codegen-units=1` (for fat LTO)

Possible values: `off`, `thin`, `fat`

### `size-opt`

Bundled preset for minimal binary size. Could combine:
- `opt-level = "z"`
- `strip = "symbols"`
- `lto = "fat"`
- `panic = "immediate-abort"`

### `opt-level` (top-level)

Promote from `[rustc]` to top-level for convenience.

## Extensibility to Other Cargo Commands

Currently xt handles: `build`, `run`, `test`

Natural extensions:
- `cargo xt clippy` - with lint configuration
- `cargo xt fmt` - format checking/fixing
- `cargo xt doc` - documentation generation
- `cargo xt bench` - benchmarking

Each command has different relevant options to translate.

## Decision: File Suffix `.xt.toml` vs `.ts.toml`

Now is the time to decide before implementing versioning and CLI management.

### Current: `.xt.toml`

- Named after the tool (`xt`)
- Example: `opt.xt.toml`, `opt-001-a1b2c3d4.xt.toml`
- Already used in docs, examples, and code

### Proposed: `.ts.toml`

- Named after "translation spec" / aligns with `cargo xt ts` alias
- Example: `opt.ts.toml`, `opt-001-a1b2c3d4.ts.toml`
- Shorter, more descriptive of content

### Tradeoffs

| Aspect | `.xt.toml` | `.ts.toml` |
|--------|-----------|-----------|
| Tool alignment | ✓ Tool is `xt` | ✗ Tool isn't `ts` |
| Content description | ✗ What is "xt"? | ✓ "translation spec" |
| CLI alias | ✗ No alias match | ✓ Matches `cargo xt ts` |
| Generality | Tied to xt tool | Could be used by other tools |
| TypeScript confusion | None | Minimal (`.ts.toml` ≠ `.ts`) |
| Migration | None | Rename existing files |

### Generality Argument

If xt becomes more general (not just cargo/rust), `.ts.toml` is tool-agnostic:
- A translation spec for gcc could also be `opt.ts.toml`
- Doesn't imply the file is only for the `xt` tool

### Decision

**Decided: `.ts.toml`** - content-centric naming for generality.

Migration order:
1. Notes are historical - leave `.xt.toml` references as-is
2. Change `TSPEC_SUFFIX` constant in xt code
3. Rename actual `*.xt.toml` files → `*.ts.toml`
4. Verify build/run work (tests should fail at this point)
5. Change `test_constants::SUFFIX` - tests pass
6. Update docs: `xt/README.md`, `README.md`, `CLAUDE.md`

## 20260130-2 - CLI Commands Status and Plan

### Already Implemented

Read-only commands are working:

```bash
cargo xt ts list [crate]     # List tspec files
cargo xt ts show [crate]     # Show tspec contents
cargo xt ts hash [crate]     # Show content hash
cargo xt compare [crate]     # Compare builds across specs
```

### Next: Modification Commands

Build on existing `ts` subcommand structure. Add modification commands that:
1. Read current spec
2. Apply modification
3. Save as new versioned file: `name-<seq:03>-<hash:08>.ts.toml`

Proposed commands:
```bash
cargo xt ts set <crate> <key> <value>      # Set a value
cargo xt ts add <crate> <key> <value>      # Add to list
cargo xt ts remove <crate> <key> [value]   # Remove key or value from list
cargo xt ts new <crate> [--from <spec>]    # Create new spec
```

### Implementation Order

1. **`ts new`** - Create empty or copy existing spec ✓
2. **`ts set`** - Set scalar values (panic, strip, target_triple, etc.) ✓
3. **`ts add`** - Append to list values (linker.args, rustc.flags, etc.)
4. **`ts remove`** - Remove from lists or delete keys
5. **Versioning** - Auto-create versioned snapshots on modification

Once CLI commands work, use them to add high-level options:
- `strip` option via `ts set`
- `lto` option via `ts set`

### Key Design Questions

1. **Which spec to modify?** - Need `-t <spec>` flag or default to `tspec.ts.toml`
2. **Key syntax** - Dotted path like `rustc.opt_level` or `linker.args`
3. **Value parsing** - Strings, bools, lists (comma-separated?)

## 20260130-4 - Add Strip Support

### Goal

Add strip functionality in two places:
1. `--strip` flag to `cargo xt test` (consistency with build/run)
2. `strip` field in tspec files (high-level option)

### CLI Flag

`build` and `run` already have `-s, --strip`. Add to `test` for consistency.

### tspec Field

Add `strip` as a high-level option (like `panic`):

```toml
strip = "symbols"  # or "none", "debuginfo"
```

Would translate to:
- `rustc`: `-C strip=symbols` (or `debuginfo`, `none`)

Values:
- `none` - no stripping (default)
- `debuginfo` - strip debug info only
- `symbols` - strip all symbols

### Implementation Order

1. Add `--strip` to `test` command CLI
2. Add `StripMode` enum to `options.rs`
3. Add `strip` field to `Spec` type
4. Apply strip in `cargo_build.rs`

### Benefit

tspec `strip` field means you don't need `--strip` on every command - it's baked into the spec. The CLI flag still useful for one-off overrides.
