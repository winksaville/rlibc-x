## xt Relationship to Cargo

### Current State

In rlibc-x, `./target/debug/xt build` works without cargo:

```bash
./target/debug/xt build -p hw-x1    # Works if xt is already built
```

But we typically invoke via `cargo xt` which:
1. Builds xt if needed (via cargo)
2. Runs xt with remaining args

### Question: Can xt Be Generalized Beyond Cargo?

The core insight: **xt is a translation layer**, not inherently cargo-specific.

What xt does:
1. Reads tspec.ts.toml (translation spec)
2. Translates high-level options to tool-specific flags
3. Invokes the underlying tool (currently cargo)

This pattern applies to any build tool:
- `xt build` → `cargo build --...` (current)
- `xt build` → `make CFLAGS="..."` (hypothetical)
- `xt build` → `gcc -o ... -O2 ...` (hypothetical)

### Bootstrapping Problem

If xt isn't cargo-specific, how does it get built?

Options:
1. **xt is always Rust** - Build with cargo once, then xt is self-sufficient
2. **Prebuilt binaries** - Distribute xt binaries
3. **Bootstrap script** - `./bootstrap.sh` builds xt using system tools

### Practical Path Forward

For now:
- xt remains cargo-focused (Rust projects)
- `cargo xt` is the primary interface
- Direct `./target/*/xt` works for avoiding cargo overhead

Future consideration:
- If xt generalizes to other languages/tools, it could be distributed as a standalone binary
- The tspec format is already tool-agnostic (`[cargo]`, `[rustc]`, `[linker]` sections)

### Design Principle

Keep xt's core generic while cargo integration is the first and primary use case. The `[cargo]` section in tspec could eventually sit alongside `[make]` or `[gcc]` sections.
