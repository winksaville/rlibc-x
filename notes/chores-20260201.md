## 20260201 - xt Relationship to Cargo

### Current State

In rlibc-x, `./target/debug/xt build` works without cargo:

```bash
./target/debug/xt build -p hw-x1    # Works if xt is already built
```

But we typically invoke via `cargo xt` which:
1. Builds xt if needed (via cargo)
2. Runs xt with remaining args

## 20260201 - The Double-Cargo Problem

```
cargo xt build -p hw-x1
  └─> cargo builds/checks xt (if needed)
      └─> runs: target/debug/xt build -p hw-x1
          └─> xt invokes: cargo build -p hw-x1 --flags...
```

Cargo is invoked twice - once to run xt, once by xt to do the actual build. The first invocation is pure overhead once xt exists.

**Options to eliminate outer cargo:**
1. Shell alias/function: `alias xt='./target/release/xt'`
2. Bootstrap script: `./xt` script that builds xt if missing, then runs it
3. Install to PATH: `cargo install --path xt` puts `xt` in `~/.cargo/bin/`
4. Makefile/justfile: `just build hw-x1` → runs xt directly

**Eliminating inner cargo (future):**

xt could invoke rustc/linker directly instead of going through cargo. This would make xt a true build system rather than a cargo wrapper:

- Current: xt reads tspec → translates to cargo/rustc flags → invokes cargo
- Future: xt reads tspec → invokes rustc directly → invokes linker directly

The second approach is more complex (dependency tracking, incremental builds, etc.) but eliminates cargo entirely from the build path. Deferred until the simpler wrapper approach hits limitations.

### Question: Can xt Be Generalized Beyond Cargo?

The core insight: **xt is a translation layer**, not inherently cargo-specific.

What xt does:
1. Reads tspec.ts.toml (translation spec)
2. Translates high-level options to tool-specific flags
3. Invokes the underlying tool (currently cargo)

This pattern applies to any build tool:
- `xt build` → `cargo build --...` (current)
- `xt build` → `make CFLAGS="..."` (hypothetical)
- `xt build` → `gcc -o ... -O2 ...` (hypothetical)

### Bootstrapping Problem

If xt isn't cargo-specific, how does it get built?

Options:
1. **xt is always Rust** - Build with cargo once, then xt is self-sufficient
2. **Prebuilt binaries** - Distribute xt binaries
3. **Bootstrap script** - `./bootstrap.sh` builds xt using system tools

### Practical Path Forward

For now:
- xt remains cargo-focused (Rust projects)
- `cargo xt` is the primary interface
- Direct `./target/*/xt` works for avoiding cargo overhead

Future consideration:
- If xt generalizes to other languages/tools, it could be distributed as a standalone binary
- The tspec format is already tool-agnostic (`[cargo]`, `[rustc]`, `[linker]` sections)

### Design Principle

Keep xt's core generic while cargo integration is the first and primary use case. The `[cargo]` section in tspec could eventually sit alongside `[make]` or `[gcc]` sections.

## 20260201 - Comments Lost on Serialization

Using `-t crate/spec.ts.toml` loses all comments in the original file. This is a serde/toml limitation - it parses to structured data, discarding comments.

Options:
- Accept that versioned snapshots are "clean" (comments live in source spec)
- Add `--comment "note"` flag to insert annotation at top of output

Middle ground for now: document that `ts set` creates clean snapshots. Add optional `--comment` flag for quick annotations.

**Future solution:** Migrate from `serde + toml` to `toml_edit` crate, which preserves comments and formatting. This is the right fix but adds complexity - defer until comment preservation becomes a pain point.
